# ai3080 — 4× → 3× RTX 3080 20GB 本地推理机：硬件 + 基准 + 踩坑

一台自建家用推理机的完整记录：硬件清单、4 卡 / 3 卡 A/B、引擎选型与调参、实测基准、以及一路上踩过的坑。
文档里的数据来自本机实测；无来源的推算会明确标注。

> 全部内容已脱敏（内网 IP、Tailscale IP、用户名、GPU UUID、主机密钥均已替换为占位符）。

## 硬件

| 项目 | 规格 |
|---|---|
| CPU | AMD EPYC 7402（24C/48T，**AVX2，无 AVX-512**） |
| 内存 | 123 GiB DDR4（实测可用约 119 GiB） |
| **原始 GPU 配置** | **4× 魔改 RTX 3080 20GB（GA102，`sm_86`，共 80 GB 显存）** |
| **当前 GPU 配置** | **3 张（60 GB）** —— 第 4 张（PCI `c4:00.0`）于 **2026-10-07 拆除** |
| GPU 位置 | 现役 3 张位于 PCI `01:00.0` / `41:00.0` / `81:00.0`（各自独立 Root Complex，Gen4 x16） |
| GPU 特殊点 | A26R 魔改卡；**BAR1 仅 256 MB、ReBAR 未生效**；VBIOS 为 2020 首发版 |
| 驱动 | NVIDIA **610.57.04** + P2P 补丁（卡对 P2P 全通） |
| 内核 | `7.0.0-31-generic`（**已 apt-mark hold**） |
| 磁盘 | Lexar NM620 256 GB NVMe（238.5 GB，**DRAM-less**） |

**时间线**：4 卡起步 → 用同一套方法学做 **4 卡 vs 3 卡 A/B** → 依据结果拆除第 4 张 → 现役 3 卡。

## 4 卡 vs 3 卡（同一方法学）

| 指标 | 4 卡 | 3 卡（现役） | 差 |
|---|---:|---:|---:|
| 聚合吞吐 N=1 | **70.4 t/s** | 59.1 t/s | 4 卡 **+19.1%** |
| 聚合吞吐 N=2 | **75.0 t/s** | 67.3 t/s | 4 卡 **+11.4%** |
| 聚合吞吐 N=4 | **97.9 t/s** | 80.8 t/s | 4 卡 **+21.2%** |
| 专家槽 / 路由覆盖 | 18,394 / 98.6% | 13,825 / 98.4% | −25% 槽位 |
| 分层（`layer_split auto`） | `K=12,25,37` | `K=15,32` | — |
| Prefill | 1,721 t/s ⚠️ | **1,941 t/s** ⚠️ | **口径不同，不可比** |
| Decode（全新 256 token，中位） | — | **64.4 t/s** | — |

⚠️ **两个 prefill 的提示长度不同**（4 卡为 19.6k 提示，3 卡为 ~31k 提示），**不可直接比较**；
真正可比的是并发聚合表（同一提示集、同一 `parallel: 4`、每路唯一 nonce）。

### 为什么拆掉第 4 张卡

**4 卡在每一档都更快（+11~21%）**，但本机以**单人使用**为主——用 +19% 的单人吞吐去换一张卡的代价不合算，
故于 2026-10-07 拆除 `c4:00.0`。（该判断由机主做出，数据如上供复核。）

### 现役 3 卡的其余实测

| 指标 | 实测 |
|---|---|
| Prefill（~31k 唯一提示，中位） | **1,941 tok/s** |
| Decode（引擎自报） | 79.9 – 93.2 tok/s（可预测内容可达 ~120） |
| 专家缓存命中率 | 96 – 99 % |
| 推理期磁盘读取 | **0**（`file_blobs`/`file_mb` 恒为 0） |
| 对话缓存 | 19,620–25,972 token 在 0.06–0.7 s 内恢复（约 100×） |
| 就绪时间 | 热页缓存 60–85 s；冷启 265 s；开视觉后 125 s |

**单人使用应关闭 `parallel`**（它是请求排队的开关；开则每 slot 约 0.6 GB 显存从专家缓存里扣）。

## 参数调优结论（2026-10-11 A/B 实测）

一组网传参数（V100 短视频，长文档场景）：`--short-read 32`、`--layer-split 24`、`--mtp-hnorm stream`、`--spec-min-p 0.8`。

| 参数 | 本机实测 |
|---|---|
| `--short-read 32` | 短提示与默认 64 无差；**长文档上输出与草稿接受率逐位相同** → 无收益 |
| `--prefill auto:32768` | **无影响**（prefill 稳定在 2,170-2,183 tok/s） |
| `--spec-min-p 0.8` | 接受率变高但**更慢**（接受率不是速度指标） |
| `--mtp-hnorm stream` | 1024-token 生成下**慢 9-12%** |
| `--layer-split 24` | **不适用**：2 卡均分点；本机 3 卡 `auto` = `K=15,32` |
| 四项组合 | 1024-token 生成下**慢 13-15%** |

**结论：本机 `--calibrate` 测出的默认值更好**（`--pcie-frac 0.00`、`--spec-min-p 0.5`、`--pool-workers 23`），网传参数来自别的硬件与口径，不能照抄。完整数据见 [docs/strata-ab-2026-10-11.md](docs/strata-ab-2026-10-11.md)。

## 三条硬红线（血泪）

1. **绝不设 `GGML_CUDA_P2P=1`** —— 出乱码且持久污染驱动状态（MTP 接受率归零，只有重启能恢复）；
2. **内核必须钉 `7.0.0-31-generic`** —— 7.0.0-34 及以上与该驱动组合会**静默损坏多卡数据**；
3. **正确性校验三件套**：`Paris` / `51` / `Jupiter`（每次改动后必须通过）。
