# BAR1 256MB 的定性：核心限制还是固件限制？

**问题**：同 GPU 核心的 RTX A5000（GA102）支持大 BAR1，为什么 3080 不行？是核心不支持，还是其他问题？

**结论**：**是固件/配置层的限制，不是核心不支持。** 但**当前无可行手段解除**。

---

## 一、先撤回我两个无效结论

我在这个问题上做了两组实验，**两组方法都有缺陷，结论无效，予以撤回**：

### 实验 1：`setpci` 写入 Resizable BAR 控制寄存器

```
写 base+0xC = 0          → 读回 0x1c00   （已知可写区域的 sanity check 都失败）
写控制寄存器 = 0x0801    → 读回 0x00000460
写控制寄存器 = 0x0400    → 读回 0x00000460
```

**连"选一个已支持的尺寸"这种完全合法的写入都被忽略。**

这说明问题是 **`setpci` 根本写不进这张卡的扩展配置空间**（可能被内核/驱动锁定，
或该 ecap 字段在本实现下只读），**而不是硬件拒绝大尺寸**。

→ 因此"硬件拒绝 >256MB 请求"这一结论**不成立，撤回**。

### 实验 2：VBIOS ROM 解剖

当时结论是"ROM 里没有 ReBAR 能力结构"。

补充验证：用 `dd` 从 512KB 的 ROM BAR 窗口读满，**实际只返回 156672 字节**
（MD5 `74833db0a26c363821e4b6cad4d86e5c`，与首次读取一致）。
即硬件暴露的就是这些，**ROM 是完整的**。

但这份 ROM 的**根镜像只有 41984 字节**（PCIR image length = 82 blocks），
其余为 UEFI/EFI 镜像。而**运行时的 config space 可能由 EFI 镜像中的驱动代码构建**——
我只搜了 `0x15` 这一种字面模式，**没有解析 EFI 镜像内部的代码路径**。

→ 因此"固件里没有该结构"这一结论**证据不足，降级为"未证实"**。

---

## 二、正确的判断：是固件问题

支持"固件限制"而非"核心限制"的证据：

| 证据 | 说明 |
|---|---|
| **GA102 同核心能做** | RTX A5000（24GB）、A6000（48GB）、3090（24GB）均为 GA102，BAR1 都可远超 256MB |
| **NVIDIA 官方用固件开 ReBAR** | 2021 年给 GeForce RTX 30 系开 ReBAR，手段就是**发布 VBIOS 更新**。若硅片做不到，发固件毫无意义 |
| **AIB 厂商能改** | 各家能发 ReBAR VBIOS，说明该能力由固件配置而非掩膜决定 |
| **消费/专业区分靠固件** | 同 die 分不同产品线，差异在固件许可与配置，不在硅片能力 |

**所以：GA102 的 BAR 解码能力足够，256MB 是这批改装卡固件层的限制。**

---

## 三、但为什么仍然无解

限制在固件层 ≠ 能改。逐条排除：

| 手段 | 结果 |
|---|---|
| 主板 BIOS（Above 4G / CSM / ReBAR） | ❌ 你已全部设对；它只是前提，不定义 GPU 的上限 |
| 内核参数（`pci=realloc` 等） | ❌ 你已全用 |
| 换 PEX88096 交换芯片 | ❌ 它不是限制源；GPU 上报多少它转发多少 |
| 换 VBIOS EEPROM 芯片 | ❌ 固件内容问题，且无 20G 版 ReBAR 固件可刷 |
| 找改装商要 ReBAR 固件 | ❌ 商家明确答复没有 |
| 刷零售版 3080 ReBAR VBIOS | ❌ 显存配置不同（10G/12G vs 20G），**必砖** |
| ReBarUEFI 注入 | ❌ 前提是设备自己声明 ReBAR |
| NvStrapsReBar | ❌ 仅支持 Turing，且同样要求 BAR1 够大 |
| 注册表键（`RMForceStaticBar1` 等） | ❌ **实测会搞坏 GPU 初始化**，两次复现 |
| 自己改 VBIOS | ⚠️ 理论路径存在，但：无参考固件、有签名/校验、失败即变砖（需 CH341A 救砖） |

**公开检索结果：没有任何 20G 改装卡成功加 ReBAR 的案例。**

## 四、如果一定要试，唯一有理论依据的路径

**前提**：接受变砖风险 + 有 CH341A 编程器 + 只在一张卡上试。

**思路**：3080 与 3090/A5000 同为 GA102。若能拿到**同板型、支持 ReBAR 的固件**
（例如某个用相同 PCB 的 20G 版本），替换后可能获得大 BAR1。

**步骤**：
```bash
# 1. 完整备份（必须用 nvflash，不要用 /sys/.../rom）
sudo nvflash --save backup.rom

# 2. 确认板卡身份
strings backup.rom | head -20
# 你的卡: "A26R RTX 3080 20GB"  VBIOS 94.02.27.00.14

# 3. 找同板型的 ReBAR 版本（目前不存在）
# 4. 刷入后立刻验证
sudo lspci -vv -s <bdf> | grep -A4 "Resizable BAR"
# 期望 supported: 出现 >= 20480MB
```

**为什么我不建议**：
- 无参考固件可比对（不像零售卡有官方 ReBAR 更新）
- 20G 是改装配置，刷错直接不点亮
- 前面所有证据都指向"这批固件没有该能力"，成功率极低

## 五、回到你的实际问题

**判断链**：

```
256MB 上限
  ├─ 核心能力？     → 否（A5000/3090 同 GA102 支持大 BAR1）
  ├─ 主板/BIOS？    → 否（已全设对，且它不定义 GPU 上限）
  ├─ 交换芯片？     → 否（下游转发，不设上限）
  ├─ 驱动？         → 否（魔改驱动已授权，topo -p2p = OK）
  └─ 固件？         → ✅ 是
       └─ 能改吗？  → ❌ 无 20G ReBAR 固件；自改无参考、高风险、成功率极低
```

**唯一可靠出路：换 BAR1 够大的卡。**

验货命令（买前让对方跑，或到手立刻验）：
```bash
sudo lspci -vv -s <bdf> | grep -A4 "Resizable BAR"
```
- `supported: 64MB 128MB 256MB` → ❌ 不能用
- `supported: ... 8192MB 16384MB 24576MB` → ✅ 可以

**你现有基础设施可完整复用**：88096 交换卡、aikitoria 魔改驱动、ACS/IOMMU 配置。
换卡后 P2P 应可直接跑通。

## 附：本次会话的教训

我在这个问题上犯了两次方法论错误：
1. 用**无效的写入实验**得出"硬件拒绝"的结论
2. 用**单一模式搜索**得出"固件里没有"的结论

两者都过早收敛。正确的做法是先验证**测量工具本身是否有效**
（例如先用一个已知可写且无害的字段做 sanity check），再下结论。
